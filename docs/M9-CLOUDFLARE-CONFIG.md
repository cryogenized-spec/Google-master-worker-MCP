# M9 — Private Cloudflare binding configuration preparation

**Status:** safe LOCAL configuration tooling only. The CLI **does not connect to Cloudflare, deploy Workers, create D1/KV, set secrets, touch DNS or link Google**.

## Purpose

This step removes the need to manually stitch together three separate Wrangler JSONC files when a Cloudflare account and managed zone are available.

It creates three **local, Git-ignored** files at the repo root:

- \`.wrangler-deploy.auth.jsonc\` — OAuth issuer Worker, KV \`OAUTH_KV\`, \`AUTH_RATE_LIMITER\`
- \`.wrangler-deploy.mcp.jsonc\` — read-only MCP resource Worker, \`DB\` D1 vault, private default RPC service binding \`AUTH_SERVER\`
- \`.wrangler-deploy.setup.jsonc\` — owner-only browser setup Worker, the same D1 \`DB\`, \`SETUP_RATE_LIMITER\`

All three generated files use \`workers_dev=false\`, \`preview_urls=false\`, **no routes**, and no deployment triggers. The MCP Worker sets \`GMW_WORKSPACE_READS_ENABLED=false\`. No secret values are included, and all files are written without group/other permissions (\`0600\`) without overwriting existing configuration.

**Important RPC correction:** \`apps/auth-server/src/index.ts\` exports its \`AuthServer\` WorkerEntrypoint as the **default export**. Cloudflare's RPC Service Binding selects a default export when \`entrypoint\` is omitted. An explicit \`entrypoint: "AuthServer"\` is for a named export and is incorrect in this repo. The generated configuration intentionally omits it.

## Data you need from your own Cloudflare account

- A domain **already owned and managed in the intended Cloudflare account**. The CLI assumes you can create \`auth.\`, \`mcp.\`, and \`setup.\` hostnames beneath that zone. Ownership is a *manual prerequisite* and cannot be proven by syntax validation.
- KV namespace ID for the OAuth provider (\`OAUTH_KV\`), exactly 32 hexadecimal characters.
- D1 vault database **name** and its actual UUID. This is one shared D1 database bound to MCP and private setup.
- Two distinct **account-unique integer** rate-limit namespace IDs, used only as the private setup and OAuth throttling namespaces. These IDs are *defined by you*, not generated by Cloudflare, and must not collide with existing account namespaces. Rate limits are approximate and local to a Cloudflare location.

Do not paste Cloudflare credentials or Google OAuth secrets into chat or into these CLI arguments. All inputs are identifiers and hostnames, not tokens.

## Local Bash procedure (Node 26)

\`\`\`bash
git switch main
git pull --ff-only
npm ci
npm test
npx wrangler login
npx wrangler whoami

# Once your own domain and resource IDs are known:
node scripts/prepare-cloudflare.mjs \
  --zone YOUR-OWNED-DOMAIN.TLD \
  --kv-id YOUR-KV-32-HEX-ID \
  --d1-id YOUR-D1-UUID \
  --db-name google-master-vault \
  --auth-rate-id YOUR-UNIQUE-INTEGER \
  --setup-rate-id YOUR-OTHER-UNIQUE-INTEGER

node scripts/prepare-cloudflare.mjs --verify
\`\`\`

The literal \`YOUR-...\` examples are **placeholders** and will be rejected. No guessed live IDs are provided or used by the program.

To inspect configuration safely without connecting to Cloudflare:

\`\`\`bash
npx wrangler deploy --dry-run -c .wrangler-deploy.auth.jsonc
npx wrangler deploy --dry-run -c .wrangler-deploy.mcp.jsonc
npx wrangler deploy --dry-run -c .wrangler-deploy.setup.jsonc
\`\`\`

A second CLI run refuses to overwrite existing local files. If you need to change an ID or domain, review and adjust the generated files manually, then run \`--verify\`. Do not commit those files; \`.gitignore\` excludes them.

## Hostnames and Google registration

For an owned zone \`yourdomain.tld\`, the CLI consistently derives:

| Purpose | Host / redirect |
| --- | --- |
| MCP client OAuth issuer | \`https://auth.yourdomain.tld\` |
| MCP resource | \`https://mcp.yourdomain.tld/mcp\` |
| Private operator setup | \`https://setup.yourdomain.tld\` |
| Operator login on the auth Worker | \`https://auth.yourdomain.tld/google/callback\` |
| Operator login on the setup Worker | \`https://setup.yourdomain.tld/google/callback\` |
| Google Workspace permission callback | \`https://setup.yourdomain.tld/oauth/google/callback\` |

Google Cloud **Web application** OAuth redirect URIs must match their actual enabled callbacks exactly. Use a separate Workspace API client if keeping consent scopes isolated from operator sign-in. Authorization code exchange and consent must take place through the browser and Worker; neither should expose refresh tokens to terminal logs or local client code.

## What is *not* configured or authorized yet

**The generated files are not deployable endpoints.** They intentionally have no routes; Google OAuth will not work until DNS, route activation, provider callback registration and Cloudflare's account-specific security controls have been reviewed. The private setup hostname must additionally be protected by WAF/Access while preserving necessary Google redirect functionality. The old developer bearer gateway is not suitable for Internet exposure.

The following still requires explicit operator-controlled deployment steps:

1. Confirm Cloudflare account ID and managed zone, choose DNS/route architecture. Authenticate Wrangler in the **intended** account.
2. Create KV and D1 resources, review and apply the \`0001\` and \`0002\` D1 migrations to the correctly identified vault database, including backup plans.
3. Configure the three Workers' **separate** Google OAuth client credentials and the same server-side AES-256-GCM key/verified Google \`sub\` for MCP and Setup. Do **not** put secret values in the generated \`vars\`. Use Cloudflare Secrets.
4. Stage a Worker version and configure secrets before routing any traffic. **Do not use ordinary \`wrangler secret put\` as an innocuous config step**: it immediately deploys a Worker. Prefer \`wrangler versions secret put\` to stage a new version, or a carefully controlled dashboard flow. Source: https://developers.cloudflare.com/workers/configuration/secrets/
5. Configure a verified private route, WAF and appropriate policies, make a disposable Google Tasks list, then activate one account connection only after an interactive test of consent, revocation and denial.
6. Enable \`GMW_WORKSPACE_READS_ENABLED=true\` for read-only MCP **only after** the vault is connected and the MCP resource token boundary is checked.

### Verification

Node 26 built-in tests validate invalid identifiers/hostnames, unsafe route activation, mismatched D1/vault IDs, incorrect OAuth callbacks, accidental read enabling, the default RPC binding, file permissions and no overwrite. CI additionally runs **Wrangler dry-run builds against three synthetic, route-free generated configurations**. CI names and IDs are fake test fixtures and never contact an account for deployment.
